C Programming

04 - Comments and Documentation
🎯 Aim: To learn how to write comments in C, why documenting code matters, and the rules that keep comments from breaking your program.
1. What is a Comment?

A comment is text in your source code that the compiler completely ignores. It exists purely for humans — to explain what a piece of code does, why a decision was made, or to temporarily disable a line while testing. C supports two comment styles.

1. Single-Line Comment //
Everything from // to the end of that line is ignored.
int age = 20; // stores the student's age
2. Multi-Line Comment /* */
Everything between /* and */ is ignored, even across several lines.
/* This program calculates
the average of three numbers
entered by the user. */
2. Example in Context
/* ------------------------------------------ Program: Simple Interest Calculator Author: Voflic Academy ------------------------------------------ */
#include <stdio.h>

int main() {
  float p, r, t, si; // p=principal, r=rate, t=time

  printf("Enter principal, rate, time: ");
  scanf("%f%f%f", &p, &r, &t);

  // Simple Interest formula: SI = (P * R * T) / 100
  si = (p * r * t) / 100;

  // printf("Debug: si = %f\n", si); ← disabled line, kept for later debugging
  printf("Simple Interest = %.2f\n", si);

  return 0;
}
The block comment at the top is documentation — a header describing the program's purpose and author, a common professional convention.
The single-line comment after variable declarations explains what each short variable name (p, r, t) actually stands for — very useful since single-letter names aren't self-explanatory.
The comment above the formula explains why the calculation looks the way it does — this kind of comment is more valuable than one that just repeats what the code obviously does.
The commented-out printf("Debug: ...") shows a very common real technique: temporarily "turning off" a line of code without deleting it, often used while debugging (see Topic 16).
⚠ Rules and Common Mistakes
  • Comments cannot be nested — writing /* outer /* inner */ still-outer */ will cause an error, because the first */ closes the comment early, leaving still-outer */ as invalid code.
  • A // comment only lasts until the end of that physical line — if it accidentally continues onto the next line without another //, that next line is treated as real code again.
  • Comments are completely removed during the Preprocessing stage (Topic 2) — they have zero effect on the compiled program's size or speed.
  • Over-commenting obvious code (e.g. i++; // increase i by one) adds noise instead of value — good comments explain why, not just restate what the code already makes clear.
Why does "Documentation" matter beyond just comments?
Good documentation also includes meaningful variable names, consistent indentation, and a clear structure (Topic 1) — comments are one tool among several that make code understandable to someone else (or to you, six months later, having forgotten your own logic).
📝 One-Line Revision: // comments one line; /* */ comments a block; both are ignored by the compiler and exist purely to make code understandable for humans.
