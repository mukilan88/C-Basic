C Programming

16 - Basic Error Messages and Debugging Techniques
🎯 Aim: To recognise the main categories of errors a C program can have, read a real compiler error message correctly, and build simple habits for finding and fixing bugs.
1. The Four Categories of Errors
1. Syntax Error
Breaks the grammar rules of C (e.g. missing semicolon). Caught at compile-time — the program will not even build.
2. Semantic / Type Error
Grammatically valid but logically inconsistent (e.g. mismatched format specifier). Often caught as a compiler warning.
3. Linker Error
The compiler understood everything, but a referenced function/variable was never actually defined anywhere. Caught at the linking stage (Topic 2).
4. Run-Time Error
The program compiles and starts, but crashes or misbehaves while running (e.g. divide by zero, array out of bounds).
5. Logical Error
The program runs completely fine, with no crash and no error message — but produces the wrong answer because of a mistake in the programmer's logic.
⚠ Logical errors are the hardest to catch — the compiler cannot detect them at all, because nothing about the code is technically "wrong." Only careful testing (checking the output against what you expect by hand) reveals them.
2. Reading a Real Compiler Error Message
int main() {
  int age = 20
  printf("%d", age);
  return 0;
}
GCC Output:
error.c:3:18: error: expected ';' before 'printf'
  3 |   int age = 20
   |                ^
   |                ;
How to decode this message:
error.c:3:18 → the error is in file error.c, on line 3, around column 18. expected ';' before 'printf' → the compiler expected a semicolon right there, but instead found the start of the next statement. The ^ mark points to the exact spot. Note: the actual missing semicolon is at the end of line 2 — compilers often report the error one token after where the real mistake is, so always check the line just above the reported one too.
3. Common Beginner Errors & Fixes
Symptom / Message Likely Cause Fix
expected ';' before ... Missing semicolon at the end of the previous line Add the missing ;
'age' undeclared Variable used before being declared, or misspelled Declare the variable first, check spelling/case
expected '}' at end of input A curly brace { was never closed Count braces carefully; use editor auto-indent to spot the gap
Warning: format %d expects int, got double Format specifier doesn't match the variable's actual type Match the specifier exactly: %d/%f/%lf/%c/%s
undefined reference to 'add' Linker error — function was declared/called but never defined Make sure the function body actually exists in the file
Program crashes / "Segmentation fault" Run-time error — often array out-of-bounds or dividing by zero Check array indices and guard against zero divisors
Output is wrong but no error shown Logical error — flawed formula or condition Trace through the logic by hand, or add debug prints (below)
4. Simple Debugging Techniques
🔍 1. Fix the First Error First
One real mistake often triggers a cascade of many reported errors.
Always scroll to the very first error in the compiler output and fix that one before worrying about the rest — recompiling often makes most of the later errors disappear on their own.
🔍 2. Compile Often, in Small Steps
Don't write 50 lines and compile once.
Compile after every small addition (a few lines at a time). This way, if an error appears, you know it must be in the few lines you just added — dramatically narrowing the search.
🔍 3. printf() Debugging
The simplest way to "see inside" a running program.
Temporarily add extra printf("here, x = %d\n", x); statements at key points to check whether variables hold the values you expect, at the moment you expect them to.
🔍 4. Read Errors Bottom-to-Top... Then Top-to-Bottom
Long error lists can be confusing.
A single typo can cause many follow-on errors below it. Read the first error message closely — it's usually the true root cause; later ones are often just side-effects of it.
💡 Golden Debugging Habit: Never guess-and-check randomly. Read the exact error message, find the exact file and line number it points to, understand why the compiler is confused there, and only then make a targeted fix — then recompile immediately to confirm.
📝 One-Line Revision: Syntax/Semantic errors are caught by the compiler, Linker errors at linking, Run-time errors while the program executes, and Logical errors give wrong output with no error at all — always fix the first reported error first, and use printf() to peek inside a running program when the bug isn't obvious.
